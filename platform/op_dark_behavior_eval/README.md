# 暗光场景行为识别测试验证算子

| 项 | 值 |
| --- | --- |
| 算子名称 | 暗光场景行为识别测试验证 |
| 算子类别 | 一级类别：事件；二级类别：行为识别 |
| 算子类型 | 测试验证算子 |
| 提交包名 | `事件_行为识别_暗光场景行为识别测试验证.zip` |
| 主入口 | `main.py` |
| 运行镜像 | `darkpipe-operator:0.1.0`（与处理算子共用同一镜像） |
| 架构 | amd64，需 1 张 NVIDIA GPU |
| 配套算子 | 暗光场景行为识别（`事件_行为识别_暗光场景行为识别.zip`） |

## 一、算子功能

对「暗光场景行为识别」处理算子做**精度评测**：读入一份带标注的视频清单，逐条推理并与标注比对，
输出总体准确率、宏平均 F1、各类别精确率/召回率/F1 以及完整混淆矩阵。

**评测路径与处理算子完全一致**，这是本算子最关键的设计约束。每条片段的处理流程是：

```
均匀抽取识别窗口所需帧数（behavior 模型为 32 帧）
  → 与处理算子同一个低照度增强算子
  → 与处理算子同一个预处理函数 preprocess_frame
  → 与处理算子同一个识别模型
  → 取概率最大的类别作为预测
```

用的就是处理算子内部调用的那几个函数，不是另写一份评测版实现。因此**评测得到的精度就是线上
会得到的精度**，不存在评测域与部署域漂移的问题。

**评测不做超分**，因为处理算子中识别器取的本来就是增强后、超分前的帧——加上超分既不改变识别
结果，又会拖慢评测。

## 二、输入参数

| 参数名 | 中文名 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `dataset_manifest` | 评测数据清单 | String | 无（必选） | 带标注的清单文件，格式见下 |
| `enhance` | 低照度增强算法 | String | `retinexformer` | `off` / `retinexformer` / `cidnet`，**须与处理算子一致** |
| `recognize` | 行为识别模型 | String | `behavior` | `r3d` / `videomamba` / `behavior` / `xclip`，**须与处理算子一致** |
| `max_clips` | 最大评测条数 | Int | `0` | `0` = 评测全部；先跑小样本冒烟时填一个小数字 |
| `gpu_ids` | GPU 卡号 | String | `0` | 评测按条串行，只取第一张卡 |
| `enhance_chunk` | 增强批大小 | Int | `4` | 每批送 GPU 的帧数，显存不足时调小 |
| `ckpt_dir` | 权重目录 | String | `/opt/darkpipe/ckpts` | 镜像内已预置默认权重，一般无需修改 |

`enhance` 与 `recognize` 必须与实际部署的处理算子取值一致，否则评测结果不能代表线上表现。

### 评测清单格式

纯文本文件，每行 `视频路径,类别标签`，逗号或制表符分隔：

```
video_path,label
/data/eval/clip_0001.mp4,drink
/data/eval/clip_0002.mp4,fall
/data/eval/clip_0003.mp4,other
```

- 允许 `#` 开头的注释行，允许一行表头（首行第二列为 `label`/`class`/`标签`/`类别` 时自动跳过）；
- 视频路径为相对路径时，按**清单文件所在目录**解析；
- **类别标签必须取自模型的类别表**。`recognize=behavior` 时为：`wave`、`throw`、`chase`、
  `fall`、`fight`、`talk`、`drink`、`pick_up`、`shake_hands`、`other`。不在表内的行会被跳过，
  并在日志与结果文件中列出原因，不会静默丢弃。

## 三、输出结果

| 参数名 | 中文名 | 说明 |
| --- | --- | --- |
| `metrics_json` | 评测指标 | 全部指标与混淆矩阵的 JSON |
| `confusion_csv` | 混淆矩阵 | 便于直接用表格软件查看的 CSV |

`metrics_json` 结构：

```json
{
  "dataset_manifest": "/data/eval/manifest.csv",
  "rows_in_manifest": 132,
  "rows_evaluated": 132,
  "rows_skipped": 0,
  "elapsed_seconds": 60.83,
  "seconds_per_clip": 0.4608,
  "accuracy": 0.8788,
  "macro_f1": 0.8212,
  "per_class": {
    "drink": {"support": 12, "precision": 0.8, "recall": 1.0, "f1": 0.8889}
  },
  "labels": ["wave", "throw", "..."],
  "confusion_matrix": [[9, 0, "..."]],
  "config": {"enhance": "retinexformer", "recognize": "behavior",
             "gpu_ids": "0", "enhance_chunk": 4},
  "skipped": [{"video": "...", "reason": "无法解码"}]
}
```

`confusion_csv` 首行首列为类别名，第 i 行第 j 列表示**真实类别 i 被预测为类别 j** 的样本数。

**宏平均 F1 只统计清单中实际出现的类别。** 若清单里没有 `fall` 的样本，`fall` 的 F1 恒为 0，
把它计入平均会无端拉低整体指标；因此 `macro_f1` 只对 `support > 0` 的类别求平均，各类别的
`support` 同时输出，便于核对覆盖了哪些类。

## 四、日志输出

规范要求测试类算子的日志至少包含处理的数据集行数与处理时间，并输出准确率、F1、召回率等指标。
本算子运行结束会打印：

```
[metrics] 数据集行数=132 实际评测=132 跳过=0
[metrics] 处理时间=60.8s 平均每条=0.461s
[metrics] 准确率(accuracy)=0.8788 宏平均F1(macro-F1)=0.8212
[metrics] 类别 wave: 样本数=12 召回率=0.7500 精确率=0.6429 F1=0.6923
[metrics] 类别 drink: 样本数=12 召回率=1.0000 精确率=0.8000 F1=0.8889
[metrics] 类别 pick_up: 样本数=12 召回率=0.9167 精确率=0.6875 F1=0.7857
[metrics] 类别 other: 样本数=96 召回率=0.8750 精确率=0.9655 F1=0.9180
```

评测过程中每 50 条打印一次进度与累计准确率，长任务不会看起来像卡死。

## 五、性能与资源

测试环境：单张 NVIDIA RTX 3090 24GB，132 条 ARID 暗光数据集片段。

| 指标 | 实测值 |
| --- | --- |
| 单条片段平均耗时 | 0.461 秒 |
| 132 条总耗时 | 60.8 秒 |
| GPU 显存峰值 | 1.04 GiB（ARID 片段分辨率较低） |
| 主机内存峰值 | 1.71 GiB |

`suanzi.json` 中 GPU 显存声明为 `8Gi`、内存 `6Gi`/`4Gi`、CPU `6`/`3`，与处理算子保持一致。
实测的 1.04 GiB 是在低分辨率片段上得到的，若评测 720p 片段，显存会升到与处理算子同量级
（约 7 GiB），因此按上限声明而不是按这次实测值声明。

评测按条串行，耗时与清单行数成正比：1000 条约需 8 分钟。先用 `max_clips` 跑几十条确认流程与
标签映射无误，再跑全量，是更省时间的做法。

## 六、上面那组数字代表什么

第四节的示例输出是**本算子的冒烟测试结果，不是模型精度指标**，两者的区别必须说清楚：

- 该测试用的是 ARID 暗光动作数据集的 132 条片段，把 ARID 的 `Drink`/`Pick`/`Wave` 三类映射为
  本模型的 `drink`/`pick_up`/`wave`，其余八类（Jump/Pour/Push/Run/Sit/Stand/Turn/Walk）**全部
  压成 `other`**；
- 因此类别分布是人为构造的（96 条 `other` 对 36 条三类行为），`fall`、`fight`、`shake_hands`
  等类别在该清单中样本数为 0，完全没有被测到；
- 0.8788 的准确率只说明**算子的评测链路是通的**（能解码、能增强、能推理、能算指标、能出文件），
  不能作为该模型在真实业务场景下 9 类行为识别能力的结论。

要得到有意义的精度指标，请用覆盖全部 9 类行为、类别分布贴近实际业务的标注数据重新评测。

## 七、注意事项

1. **输出路径的父目录由算子自行创建**，符合规范对 `outputPath` 的要求，无需框架预建。
2. **`hdfs://` 清单地址依赖容器内的 HDFS 客户端。** 算子会尝试 `hdfs dfs -get`，没有该命令时
   打印明确错误并以非零码退出。注意：即使清单文件本身能取到，**清单里指向的视频路径也必须在
   容器内可直接访问**。
3. **清单中的视频若无法解码会被跳过**，不会中断整个评测；跳过的条目与原因记录在
   `metrics_json` 的 `skipped` 字段（最多列出 50 条）与日志中。
4. **`recognize` 不提供 `off` 选项**——没有识别器就无从评测，选了会直接报错退出。
5. 任何异常都会打印完整调用栈并以非零退出码结束，框架据此判定任务失败。

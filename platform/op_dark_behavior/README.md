# 暗光场景行为识别算子（处理算子）

| 项       | 值                                                              |
| -------- | --------------------------------------------------------------- |
| 算子名称 | 暗光场景行为识别                                                |
| 算子类别 | 一级类别：事件；二级类别：行为识别                              |
| 算子类型 | 处理算子                                                        |
| 提交包名 | `事件_行为识别_暗光场景行为识别.zip`                          |
| 主入口   | `main.py`                                                     |
| 运行镜像 | `darkpipe-operator:0.2.0`（自带基础镜像，见「运行环境」一节） |
| 架构     | amd64，需 1 张 NVIDIA GPU                                       |

## 一、算子功能

面向**夜间、地下车库、无照明室内等低照度监控视频**的一体化处理算子。一次调用完成三件事：

1. **低照度增强**——把几乎看不清内容的暗帧恢复成可读画面；
2. **行为识别**——在增强后的画面上判定人员行为，输出带时间戳的事件；
3. **超分辨率放大 + 标签叠加**——放大输出画面，并把识别结果叠在画面底部，便于人工复核。

三个环节的顺序是**增强 → 识别 → 超分**。识别取的是**增强之后、超分之前**的帧，原因有三：
识别模型本身就是在增强帧上训练的；识别预处理会把画面缩放到 224×224，超分放大的像素随即被丢弃；
实测超分对识别结果无影响。把超分放在识别之后，等于用零精度收益换取识别环节的额外耗时。

### 可识别的行为

`recognize` 取默认值 `behavior` 时，输出以下 9 类行为，外加 1 个兜底类：

| 标签      | 含义     | 标签            | 含义                   |
| --------- | -------- | --------------- | ---------------------- |
| `wave`  | 挥手     | `talk`        | 交谈                   |
| `throw` | 投掷物品 | `drink`       | 喝水                   |
| `chase` | 追逐     | `pick_up`     | 捡拾物品               |
| `fall`  | 跌倒     | `shake_hands` | 握手                   |
| `fight` | 打斗     | `other`       | 其他日常活动（兜底类） |

`other` 是有意保留的：没有它，每个识别窗口都会被强行归入 9 类之一，普通走动也会被报成某种行为。
事件文件中的 `label` 字段给出的是可读名称（如 `drink` 显示为 `Drinking water`）。

## 二、输入参数

| 参数名            | 中文名           | 类型   | 默认值                  | 说明                                                                                                     |
| ----------------- | ---------------- | ------ | ----------------------- | -------------------------------------------------------------------------------------------------------- |
| `video_path`    | 待处理视频       | String | 无（必选）              | 线上默认为实时流：国标(GB28181，经网关转换为可拉流地址) / `rtsp://` / `http(s)://`（flv、hls）；也支持容器内本地路径。**不使用 `hdfs://`** |
| `enhance`       | 低照度增强算法   | String | `retinexformer`       | `off` / `retinexformer`                                                                            |
| `sr`            | 超分辨率算法     | String | `bicubic`             | `off` / `bicubic`                                                                                   |
| `sr_scale`      | 超分放大倍数     | Int    | `2`                   | `2` / `3` / `4`，`sr=off` 时忽略                                                                 |
| `recognize`     | 行为识别模型     | String | `behavior`            | `off` / `behavior`                                                                                  |
| `reco_span_sec` | 识别窗口时长(秒) | Float  | `1.0`                 | 每次判定依据最近多少秒的画面                                                                             |
| `max_frames`    | 最大处理帧数     | Int    | `0`                   | `0` = 整段视频；**处理国标/`rtsp://`/`flv`/`hls` 等实时流时必须填正整数**，用来限定单次调用截取的时长 |
| `label_bar`     | 叠加标签条       | Bool   | `true`                | 关闭后输出纯画面，事件仍写入 JSON                                                                        |
| `gpu_ids`       | GPU 卡号         | String | `0`                   | 逗号分隔，如`0,1,2,3`，多卡时按帧区间分片并行                                                          |
| `enhance_chunk` | 增强批大小       | Int    | `4`                   | 增强阶段每批送 GPU 的帧数，显存不足时调小                                                                |
| `ckpt_dir`      | 权重目录         | String | `/opt/darkpipe/ckpts` | 镜像内已预置默认配置所需权重，一般无需修改                                                               |
| `local_output_dir` | 本地落地目录(可留空) | String | 无（**可留空**） | 容器内目录，如 `/mnt/nfs/darkout`；把结果直接写到平台挂进来的 NFS，事后本地浏览                        |
| `hdfs_output_dir` | HDFS落地目录(可留空) | String | 无（**可留空**）     | 如 `hdfs://用户名@ip:port/a/b`；与 `local_output_dir` **至少填一个**                                      |

**`reco_min_conf`（行为判定阈值）**：最高分的具名行为达不到该值时报为 `other`，用于压制低置信度
误报；`0` 表示关闭。先按 `0` 跑一遍看置信度分布再定值。

**`color_saturation`（色彩饱和度）**：增强会把画面拉灰（平均彩度 5.9），本参数在 Lab 空间缩放色度，
色相严格不变，建议 2.0-2.6（2.6 时彩度 15.2）。在识别之后进行，不影响识别结果。

### 必填参数

按规范「有 `default` 字段即代表该参数必填、不能为空值」——没有 `default` 字段的三个参数如下，
其余 10 个不填也会取默认值：

| 参数名 | 是否必填 | 为什么 |
| --- | --- | --- |
| `video_path` | **必填** | 每次处理的视频/流地址都不同，没有通用默认值 |
| `local_output_dir` | 可留空 | 留空则不另存本地 |
| `hdfs_output_dir` | 可留空 | 留空则不上传 HDFS |

**但 `local_output_dir` 与 `hdfs_output_dir` 不能同时留空。** 框架 `outputPath` 指向的文件只
存在于容器内，容器退出即不可再取；两个都不填等于这次运行的结果谁也拿不到。算子会在**开始
处理之前**就检查并报错退出，而不是白跑几分钟 GPU 再告诉你没地方放。

两个目录可以同时填，此时同一次运行在两边落到**同名子目录**下，便于对照。

### 各选项怎么选

**`enhance`（低照度增强）**

- `retinexformer`——**默认，推荐**。速度最快、在极暗场景下最稳。
- `off`——输入本身照度正常时才用，可省下大部分耗时。

**`sr`（超分辨率）**

- `bicubic`——**默认，推荐**。CPU 双三次插值，只占 2–6% 的吞吐量。
- `off`——不放大。720p 及以上输入建议关闭超分，见「性能实测」。

**`recognize`（行为识别）**

- `behavior`——**默认，推荐**。VideoMamba-Tiny 在上述 9 类行为 + `other` 上微调。
- `off`——只做增强与超分，不做识别，事件文件输出空数组。

## 三、输出结果

| 参数名           | 中文名   | 说明                                      |
| ---------------- | -------- | ----------------------------------------- |
| `output_video` | 输出视频 | 增强 + 超分 +（可选）底部识别标签条的 mp4 |
| `events_json`  | 识别事件 | 行为事件 JSON 数组                        |
| `summary_json` | 运行汇总 | 帧数、耗时、帧率、行为统计与生效配置      |

**三个输出文件除了写入框架的 `outputPath` 之外，还会另存一份到 `local_output_dir`（通常是挂进
容器的 NFS 目录）和/或 `hdfs_output_dir`。** 容器退出后 `outputPath` 指向的本地文件即不可再取——镜像不落盘保存产出，
`outputPath`/`inputPath` 之间的传递也只发生在同一次编排内部——因此生产环境要事后取回结果，
必须走这两份拷贝之一。实际落地路径是 `<目录>/<时间戳>_<进程号>/<文件名>`，每次运行落到独立
子目录，不会互相覆盖；两个目录都填时用的是**同一个子目录名**，两边对得上。日志中会打印形如
`[done] 输出视频(本地) -> /mnt/nfs/darkout/<YYYYmmdd_HHMMSS>_<pid>/output_video.mp4`
`[done] 输出视频(hdfs) -> hdfs://.../<YYYYmmdd_HHMMSS>_<pid>/output_video.mp4` 的行给出确切地址。

`events_json` 样例：

```json
[
  {"label": "Drinking water", "score": 0.87, "frame_index": 32, "timestamp": 1.07},
  {"label": "Picking up object", "score": 0.71, "frame_index": 48, "timestamp": 1.60}
]
```

`summary_json` 样例：

```json
{
  "input": "/data/night_01.mp4",
  "output_video": "/out/output_video.mp4",
  "frames": 900,
  "frames_written": 900,
  "seconds": 37.102,
  "fps": 24.26,
  "wall_seconds": 42.645,
  "gpu_count": 1,
  "event_count": 55,
  "majority_label": "Drinking water",
  "majority_tied": false,
  "label_counts": {"Drinking water": 41, "Other": 14},
  "config": {"enhance": "retinexformer", "sr": "bicubic_x2", "sr_scale": 2,
             "recognize": "behavior", "gpu_ids": "0", "reco_span_sec": 1.0,
             "enhance_chunk": 4}
}
```

`majority_label` 是事件中出现次数最多的行为。**出现次数并列时 `majority_tied` 为 `true`**，
此时 `majority_label` 取最先出现的那个标签（结果确定，但并列意味着这段视频没有单一主导行为，
请以 `label_counts` 和 `events_json` 的时间序列为准，不要只看 `majority_label`）。日志中的
`[metrics]` 行也会在并列时标注「(并列)」。

其中 `seconds` / `fps` 是**处理段**的耗时与帧率（不含模型加载），`wall_seconds` 是**含模型加载**
的总耗时。两个数都给出来，是为了让吞吐量指标不被一次性的启动开销（约 5–6 秒）拖低，同时又不
隐瞒真实的端到端时间。`summary_json` 体积很小，下游算子可以直接以 `inputValue` 方式读取内容。

## 四、性能实测

测试环境：单机 6×NVIDIA RTX 3090 24GB，测试视频由 ARID 暗光数据集片段拼接而成，900 帧。
下表**每一行都是一次全新进程的完整调用**——平台每次调度算子都是新进程，因此表中的
「端到端耗时」包含模型加载，是用户真正会等待的时间。

| 输入分辨率 | 配置                                               | GPU 卡数 | 处理帧率             | 端到端耗时        | 是否达标              |
| ---------- | -------------------------------------------------- | -------- | -------------------- | ----------------- | --------------------- |
| 640×480   | `retinexformer` + `bicubic ×2` + `behavior` | 1        | **24.3 帧/秒** | 42.6 秒           | ✅ 高于 15 帧/秒目标  |
| 640×480   | 同上，`sr_scale=3`                               | 1        | **19.0 帧/秒** | 21.5 秒（300 帧） | ✅ 高于目标           |
| 1280×720  | `retinexformer` + `bicubic ×2` + `behavior` | 1        | 8.0 帧/秒            | 118.1 秒          | ❌ 低于 10 帧/秒底线  |
| 1280×720  | 同上                                               | 4        | 11.2 帧/秒           | 80.2 秒           | ⚠ 高于底线，低于目标 |
| 1280×720  | `retinexformer` + `sr=off` + `behavior`      | 4        | **17.7 帧/秒** | 51.0 秒           | ✅ 高于目标           |

**结论与选型建议：**

- **640×480 及以下：单卡默认配置即可**，24.3 帧/秒，高于 15 帧/秒目标 62%。
- **1280×720：单卡不达标（8.0 帧/秒），必须用多卡。** 但只加卡不够——4 卡配 `×2` 超分只有
  11.2 帧/秒。原因是分片只并行了 GPU 计算，而 `×2` 超分把每个分片的**主机侧**开销（放大、
  画标签条、编码 2560×1554 的 mp4）放大了约三倍，四个进程争抢 CPU 编码。
  **720p 的推荐配置是 `gpu_ids=0,1,2,3` + `sr=off`，实测 17.7 帧/秒达标。**
- 视频越长，模型加载的一次性开销摊得越薄：同样 640×480 单卡，300 帧任务处理帧率 20.8 帧/秒，
  900 帧任务 24.3 帧/秒。

**多卡分片的代价（务必知悉）：** 多卡是把视频按帧区间切成连续几段并行处理再拼接。每段的识别
窗口都从空开始，所以**接缝处会少若干个事件**——实测 900 帧 720p 视频，单卡输出 55 个事件，
4 卡输出 52 个。若业务对事件完整性敏感（如跌倒告警不容漏报），请用单卡处理，或把分片数降到
必要的最小值。另外每段不少于 120 帧，视频太短时算子会自动减少实际使用的卡数并在日志中说明。

**关于实时性：** 线上默认部署形态是实时流输入——`video_path` 填国标(GB28181)/`rtsp://`/
`http(s)://`（flv、hls）地址，配合正整数 `max_frames` 限定单次调用截取的时长。算子本身仍是
**离线处理算子**：平台算子的运行模型是「跑完即结束、以文件交换数据」，与持续输出的常驻实时
流服务不同——算子按 `max_frames` 截取实时流中的一段，当成一段有限长度的视频离线处理、写文件、
退出，不会常驻拉流。项目本身另有一个常驻的实时流服务（`darkpipe/server.py`，≤1 秒延迟，实测
640×480 下捕获到输出为 25–274 毫秒），但那是完全不同的部署形态（持续运行的服务进程，不是跑完
即结束的算子调用），不在本算子交付范围内。

## 五、资源需求

`suanzi.json` 中声明的资源全部来自实测，不是估计值：

| 资源                  | 声明值            | 实测依据                                                                             |
| --------------------- | ----------------- | ------------------------------------------------------------------------------------ |
| GPU 显存              | `8Gi`           | 640×480 峰值 2.4 GiB，1280×720 峰值 7.0 GiB（`enhance_chunk=4`），按 720p 留余量 |
| 内存 limits / request | `6Gi` / `4Gi` | 主机内存峰值 RSS 1.97 GiB，留出解码缓冲余量                                          |
| CPU limits / request  | `6` / `3`     | 处理过程中峰值约 5 个核（解码、编码、超分各占一个线程）                              |
| GPU 卡数              | `1`             | 默认单卡；多卡分片需在平台上为该算子申请对应卡数                                     |

`enhance_chunk` 对显存的影响是线性的，对速度几乎没有影响：640×480 下取 4 与取 8 的吞吐量分别为
27.3 / 27.9 帧/秒（同进程预热后测量），而显存占用是 2.4 GiB 对 4.7 GiB。因此默认值取 4——
用几乎为零的速度代价换一半显存。显存更紧张时可继续调小到 2 或 1，此时速度才会明显下降。

## 六、运行环境

镜像 `darkpipe-operator:0.2.0` 由本算子随包提供的 `Dockerfile` 构建（构建方法见交付包中的
`DEVELOPING.md`）。

**关于 Python 版本：** 规范推荐使用 Python 3.5–3.9，本算子使用 **Python 3.10**。原因是行为识别
模型 VideoMamba 依赖的 `mamba-ssm` / `causal-conv1d` CUDA 扩展，官方只提供 `cp310` 预编译 wheel，
且必须与 torch 2.7 / CUDA 12 / cxx11abi 严格对应；降到 3.9 就只能在容器内现场编译 CUDA 扩展，
既拖慢构建又引入不确定性。规范明确规定「如预置镜像不满足条件，需要单独提供算子运行基础 docker
镜像」，本算子据此自带基础镜像，并非违反规范。

镜像内只包含**运行环境与模型权重**，不包含算子源码；源码随 zip 包提交，由框架注入容器后以
`suanzi.json` 中的 `command` 启动。这样源码只有一个来源，不会出现镜像与 zip 中代码版本不一致。
默认配置所需的两个权重（低照度增强 `NTIRE.pth`、行为识别 `videomamba_t_behavior_32f.pth`，
合计约 35 MB）已预置在镜像的 `/opt/darkpipe/ckpts` 下，**运行期不下载任何模型**。

**镜像已实测可用（非仅构建通过）。** 在 `docker run --gpus all` 下把交付 zip 只读挂载进容器、
按 `suanzi.json` 的 `command` + `args` 启动，900 帧 640×480 视频处理帧率 **22.9 帧/秒**，端到端
45.7 秒，输出 55 个事件——与宿主机同一配置的 24.3 帧/秒相比约低 6%，属容器正常开销，仍高于
15 帧/秒目标。容器内 `torch.cuda` 识别到全部 6 张 RTX 3090，`mamba_ssm` / `causal_conv1d`
CUDA 扩展可正常导入。镜像体积约 17.8 GB（压缩后约 6.4 GB），主要是 torch 与 CUDA 运行库。

## 七、注意事项

1. **输出路径的父目录由算子自行创建。** 规范要求 `outputPath` 对应的目录由算子代码创建，本算子
   在处理开始前就会创建全部三个输出的父目录，无需框架预建。
2. **框架不保证输出路径带扩展名。** 若 `output_video` 的路径没有 `.mp4` 等视频扩展名，算子会
   先写入带扩展名的临时文件、结束时改名到框架指定的路径——因为 OpenCV 依赖扩展名选择封装格式，
   直接写无扩展名路径会失败。使用者无需为此做任何配置。
3. **`video_path` 不使用 `hdfs://`，前端呈现为文本输入框而非文件选择器。** 线上输入统一走
   国标(GB28181)/`rtsp://`/`http(s)://`（flv、hls）实时流地址，均由 OpenCV 直接打开，
   `oputil.py` 中的 `fetch_input` 对非 `hdfs://` 地址原样传递，无需下载落盘。`video_path` 是
   流地址而不是共用文件库里挑选的文件，因此 `suanzi.json` 中其 `component` 是 `stringInput`
   （字符输入框），使用者手动输入地址，而不是从文件选择器里选。`fetch_input` 仍保留
   `hdfs://` 分支（`hdfs dfs -get` 落盘，无客户端时打印明确错误退出），供配套测试验证算子的
   `dataset_manifest` 参数复用，但本算子的 `video_path` 不会用到这条路径。
4. **处理国标/`rtsp://`/`flv`/`hls` 等无限流时必须设置 `max_frames`**，否则算子不会自行结束。
5. **`hdfs_output_dir` 若为 `hdfs://` 地址，依赖容器内的 HDFS 客户端上传输出。** 走的是
   `oputil.py` 中的 `upload_outputs`：`hdfs://` 地址用 `hdfs dfs -put`/`hadoop fs -put`，没有
   客户端时打印明确错误并以非零码退出；填非 `hdfs://` 的普通目录（如框架挂载的本地/NFS 路径）
   则直接复制文件，不依赖 HDFS 客户端。
6. **日志与失败判定。** 所有日志通过 `print` 输出到标准输出，由框架收集。运行结束会打印一行
   `[metrics] frames=... seconds=... fps=... wall_seconds=... events=... label=...` 便于检索。
   任何异常都会打印完整调用栈并以非零退出码结束，框架据此判定任务失败。
7. **精度评测请使用配套的测试验证算子**「暗光场景行为识别测试验证」
   （`事件_行为识别_暗光场景行为识别测试验证.zip`），它与本算子使用完全一致的推理路径。

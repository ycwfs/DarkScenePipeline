# 逐人实时输入输出及动作片段保存核验

## 结论与适用范围

已按用户确认的规则实现“人物ID＋动作独立保存完整画面、允许时间重叠”，并接入三卡逐人候选。
本机RTSP输入、RTSP/RTMP实际接收、输入停帧/重启、输出服务器重启、观看端重连、SIGTERM停止均有实测。
最终候选没有发生服务异常退出或片段收尾协议错误；关闭额外片段去噪后，已测录制队列没有丢帧。

测试使用RTX3090物理2/3/4：1卡增强/人体/姿态、2卡逐人动作推理。模型、400×224×32输入、alpha0.7、阈值0.75、照度门75保持不变，不使用物体先验。
输入是现场原始挥手视频，通过FFmpeg按真实帧率发布到本机MediaMTX；短视频循环用于稳定性测试，不能作为连续动作精度评估。
这是原生环境、本机回环网络和本地SSD验证；没有进入平台容器、真实摄像头链路或NFS/HDFS。
生产旧包仍使用全局动作事件，未自动获得这里的逐人能力。

## 为什么旧保存器不能直接用于多人

`platform/dark-demo-v2/darkpipe/clips.py`的`ClipRecorder`仅有一个`_active`片段，接收一个全局标签。
同标签延长；另一个标签连续命中两次会提前结束旧片段、开启新片段。它不能分别处理甲喝水和乙挥手，切换时也不能保证旧动作再保留完整2秒尾部。

逐人候选按`会话、人物ID、历史代次、动作`管理独立录制器，并共享完整画面的时间缓冲。
每个录制任务使用独立暂存目录和唯一编号，解决同秒同动作文件名相撞的问题。
异步结果先按源画面时间对齐；保存链等待1.2秒让结果到齐，直播不等待。超时结果明确计入`late_action_events`，不会静默配给较新的画面。

## 确认后的保存规则

| 情况 | 保存方式 |
|---|---|
| 同一人持续同一动作 | 合并为连续片段，最后一次合格命中后再保留2秒 |
| 甲喝水、乙挥手同时发生 | 各自保存完整画面，两个文件允许重叠；文件名与JSON分别标注人物和动作 |
| 两人同时喝水 | 分别保存两个文件，人物ID不同，不合并成一个全局喝水事件 |
| 同一人从喝水变成挥手 | 喝水继续保留自己的尾部，挥手建立自己的前置缓冲；两个文件可重叠 |
| other或低于0.75的具名动作 | 不触发动作片段 |
| 长动作超过15秒 | 分成多个不超过约15秒的片段，后续片段重新带前置缓冲，时间范围重叠；单文件不是完整长动作，需连同后续分段查看 |
| 输入断流、停止服务 | 释放编码器、保存已收到的画面，标注不完整尾部；不会凭空生成摄像头缺失的内容 |
| 重连或人物历史重置 | 使用新的代次，避免把新人物/新流拼入旧事件 |

例如甲在3–6秒持续被识别为喝水，乙在4–8秒持续被识别为挥手，得到约1–8秒与2–10秒的两份完整画面视频。
文件名形如`E000_T002_G000_R00003_20261023_202000_wave_0001.mp4`，其中`T002`为跟踪人物编号。
它不是持久身份识别ID，遮挡、跟踪失败或重连后可能变化。

默认前置2秒、后置2秒、单文件最长15秒。JSON记录实际源时间范围、触发时间、人物ID、代次、关闭原因、可用前后文和写队列丢帧数。
`context_complete`只说明已识别事件附近的前后文是否齐全，并不证明模型没有漏识实际动作。
刚启动或重连后缓存不足2秒、动作漏识、长动作分段、断流或进程被强杀都不能保证单文件包含完整真实动作。

## 实际测试结果

| 测试 | 保存结果 | 录制队列丢帧 | 服务结果 |
|---|---|---:|---|
| 4分钟真实流，片段fast去噪 | 36段 | **179** | 无异常退出，但录制完整性不通过 |
| 4分钟真实流，片段去噪off | 34段 | **0** | 无弃段、强制释放、写入错误或未收尾片段 |
| 最终候选约78秒，故障注入＋SIGTERM | 10段 | **0** | RTSP/RTMP实际解码，断流提示与正常停止通过 |
| 4路完整画面同时录制，受控事件 | 4段 | **0** | 每段前置约2秒、后置约2.04秒 |
| 8路完整画面同时录制，受控事件 | 8段 | **0** | 每段前置约2秒、后置约2.04秒 |

并发容量测试写入1440×808画面，每组12秒、25fps输入；动作事件人为注入，GPU识别不在这个容量测试中运行。因此它证明8路录制本身可行，不证明8人原始视频完整识别链已达到平台性能指标。

4分钟off配置在正常输入区间实际处理19.94–20.56个新帧/秒；包含故意断流的整场均值18.33fps。
最终短故障测试正常区间18.50–20.67fps；包含两次输入中断的整场均值14.79fps。重复直播帧不算处理帧。
393/393和105/105个已提交逐人窗口完成，最大模型决策时延分别0.238、0.260秒。
仍存在输入最新帧策略的丢源帧，不能把“录制队列零丢帧”说成“摄像头所有原始帧均保存”。

本轮发现fast额外去噪在并发写盘时仍会耗尽队列，因此独立实时候选默认`clip-denoise=off`。
这仅关闭片段重复去噪，Retinexformer增强照常运行；生产清单当前默认quality未在本轮更改。

## 实际接收与恢复

接收端解码输出顶部的源帧编号，与处理记录配对计算“本机捕获该帧→接收端解码”的时间。
不是用ffmpeg进程存活或stdin写入帧率代替实际收到画面，也不包含摄像头曝光/上游编码前的时间。

最终候选低缓冲FFmpeg接收端：

| 协议 | 正常区间P95 | 正常区间最大 |
|---|---:|---:|
| RTSP | 0.294秒 | 0.404秒 |
| RTMP | 0.256秒 | 0.361秒 |

RTSP初始观看端收到1158帧，重连观看端316帧；RTMP收到1347帧。两路均收到195帧明确的断流提示画面；提示画面不送入动作片段。
源恢复发送后约0.85–0.91秒收到新画面；源进程重启后约3.22–3.24秒；RTSP观看端重连约0.71秒。
输出中继重启后约8.94秒恢复RTSP、11.76秒恢复RTMP，存在重试退避和重新建流等待，**不能承诺网络故障期间零停顿或1秒恢复**。
这些恢复时间与正常状态下的识别时延是不同指标。

早期接收工具问题也保留在证据里：OpenCV的RTMP接收出现解码/连接兼容问题；切换系统FFmpeg后RTMP正常。
4分钟off轮的RTSP客户端错用了`rw_timeout`，该轮RTSP接收核验未通过，不能标成双协议全部通过。
最终轮改用本机FFmpeg RTSP支持的`stimeout`后，两路均实际解码。该测试工具修正不涉及模型或生产推流实现。

## 断流、过载与剩余部署工作

受控静默RTSP端验证：旧生产`open_capture`在7秒探针期限内未返回；候选设置打开3秒、读取2秒超时并重连。
这些是单次I/O配置，不等于完整故障恢复上限；重试退避、网络缓存、关键帧和接收端行为都会增加等待。
候选在输入超过2秒没有新帧时显示重连提示，避免旧动作标签一直冻结在“实时”画面中。

10项新录制回归、7项优化调度回归及32项现有服务/片段回归通过，共49项。
92个实际产出MP4完整解码，共17276帧，H.264、帧数与时长核对通过；其中也包含fast轮的文件，能解码不代表没有掉过动作帧。
测试结束没有遗留本轮中继/推流子进程，已接受的片段全部排空。

当前候选保留完整诊断列表，适合有限时长实验。进入无限常驻平台前仍需接入有界日志、平台健康接口、多人事件输出格式、NFS/HDFS交付，并在目标镜像和真实平台网络验证。
存储长期跟不上时，有界队列仍可能丢帧；当前指标会明确暴露丢帧、弃段和写入失败，不能保证任意人数和磁盘故障下无损。
本轮没有替换生产算子包、Box包、模型或镜像，也没有把本机验证写成平台验收。

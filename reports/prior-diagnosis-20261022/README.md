# 现场物体、人体检测与动作先验失效诊断（2026-10-22）

结论：此前“先验不准”应拆成**观测不可靠、规则不充分、缺失证据处理错误**三件事。
喝水需要容器等常识有用，但“当前检测器没检出容器”不能证明没有喝水。
暗光中人的轮廓、关节和小物体本来就缺少有效信息；把图像拉亮并不保证这些模型会更准确。

本次仅新增诊断脚本、结果和对比图。未修改生产代码、模型、算子包或镜像。

## 测试口径

- 直接使用当前包中的 `yolo26m_detect.onnx`、`rtmo-s_end2end.onnx` 和 `NTIRE.pth`，GPU 1。
- 选取既有问题视频 `喝水16`、`捡东西2`、`喝水8`、`捡东西1`、`挥手18`，每段均匀抽 12 帧，共 60 个不同视频帧。
- 对比原始 1920×1080 整帧、部署缩放后的 720×404 原图、720×404 Retinexformer 增强图；两段亮场另测原始分辨率的人体裁剪和交互区域裁剪。
- 检测器输入固定 `[1,3,640,640]`，输出 `[1,300,6]`；统一等比例缩放和灰色补边。探针读取低分结果用于阈值扫描，部署阈值仍是 `DET_CONF=0.25`。
- 姿态指标是“至少一个人的平均关节分数 ≥0.5 的帧数”，**不是有人工关节标注的姿态准确率**。
- 数据没有人体框、物体框和关键点真值；检出帧数也不是召回率，非人框数量不是正确物体数量。样本按既有失败案例选择，不代表完整数据分布。
- 暗场诊断主动执行检测/姿态，用于观察问题。当前生产默认照度门会在这些暗场跳过骨架分支，这些数字不代表默认配置实际执行了暗场骨架。

复现入口：[probe.py](scripts/probe.py)，完整分数、框、关键点、视频和模型 SHA256：[results.json](results.json)，汇总：[summary.json](summary.json)。

## 一、亮场漏物体：小目标、遮挡和类别定义共同限制

| 喝水16，每种输入 12 帧 | 容器检出帧数 @0.25 | @0.10 | @0.05 | 所有帧中最高容器分数 |
|---|---:|---:|---:|---:|
| 1080p 原图整帧 → 检测输入640 | 0 | 0 | 0 | 0.016 |
| 原图720 → 检测输入640 | 0 | 0 | 0 | 0.016 |
| 增强720 → 检测输入640 | 0 | 0 | 0 | 0.023 |
| 原始分辨率人体裁剪 → 检测输入640 | 0 | 1 | 3 | 0.100 |
| 原始分辨率交互区域裁剪 → 检测输入640 | 0 | 1 | 1 | 0.149 |

阈值全部采用代码里的严格 `>` 比较；表中最高分仅为显示舍入。裁剪区域随人体框变化，人体裁剪和交互裁剪不是固定倍率实验。

这说明仅把检测阈值从 0.25 降到 0.1/0.05，不能解决此样本的整帧容器漏检。
裁剪可提高部分候选分数，但默认阈值下仍未检出容器，不能宣布“裁剪已解决”。
从 [原始分辨率局部图](visual/喝水16_34_interaction_crop.jpg) 可看到容器被手和脸遮挡，杯盖、容器主体的外观不完整；在整帧640输入中，其宽度约十几个像素（人工观察估计，非标注框）。
直接给检测器1080p整帧仍会缩至640；单独提高流水线720上限不会保留这些小物体的原始像素尺度。

`捡东西2` 的 [局部图](visual/捡东西2_32_interaction_crop.jpg) 显示被捡物类似纸张/薄片。
模型元数据确认使用 COCO 80 类，**没有通用“纸张”或“任意物体”类别**；因此“能检测任意被捡物”这个假设不成立。
这段视频增强后 12 帧中有 1 帧输出非人框，类别是 `tennis racket`，不能当成正确检出被捡物。
局部裁剪还会产生 `dog`、`tennis racket` 等不正确类别，放大不自动解决领域和类别问题。

需要收窄旧结论“现场只检得出人”：旧 JPEG/6帧检查描述的是当时样本。
本次 `喝水16` 增强后 8/12 帧输出了非人框，但其中包括把大厅背景误报成 `train`、把手边小圆物误报成 `sports ball`。
**可靠检出动作相关物体**才是先验需要的能力，而非输出任意非人框。

## 二、暗场漏人/漏姿态：增强亮度不能等价于恢复可检测特征

以下均在720处理尺寸下，YOLO人体阈值0.25，姿态为上述平均关节分数指标。

| 视频 | 平均亮度 原图→增强 | YOLO检出人的帧数 原图→增强 | RTMO姿态可用帧数 原图→增强 |
|---|---:|---:|---:|
| 喝水16（亮） | 139.1→168.2 | 12/12→11/12 | 12/12→12/12 |
| 捡东西2（亮） | 150.1→176.7 | 12/12→12/12 | 12/12→12/12 |
| 喝水8（极暗） | 2.4→15.4 | 0/12→0/12 | 1/12→0/12 |
| 捡东西1（暗） | 31.0→109.3 | 2/12→1/12 | 7/12→2/12 |
| 挥手18（暗） | 20.5→75.1 | 5/12→2/12 | 7/12→3/12 |

查看 [捡东西1对照](visual/捡东西1_comparison.jpg)、[挥手18对照](visual/挥手18_comparison.jpg)、[喝水8对照](visual/喝水8_comparison.jpg)。
图中绿色框是person，橙色框是非人预测，蓝线是满足绘制分数条件的RTMO骨架；数字类别对应模型COCO索引。

可观察到明显彩色噪声、块状纹理、色偏，人物衣服与背景边界不清。增强拉亮了这些现有信号，部分帧的检测与姿态输出反而减少。
结果支持“增强图与通用检测/姿态模型不匹配”的解释；本次没有分别量化传感器噪声、视频压缩、增强算法和训练域差异各自的贡献。
这里的结论限于选中的暗场失败案例，**不证明Retinexformer在所有暗场都有负收益**，也不证明VideoMamba动作识别在这些帧上一定更差。

历史全量亮度检查包含390段、4680帧，其中动作命名视频2100帧；在当时的840处理链上：

| 原图亮度区间 | 样本帧数 | 姿态可用帧比例 | 至少检出一人的帧比例 |
|---|---:|---:|---:|
| <15 | 314 | 88/314 = 28.0% | 145/314 = 46.2% |
| ≥75 | 888 | 887/888 = 99.9% | 882/888 = 99.3% |

依据：[historical-availability.json](historical-availability.json)，原始文件 `/tmp/lum_curve.jsonl` 的哈希已保留。
这纠正了旧文档“≥75后恒为1.000”的绝对表述。它也是**出现率代理指标**，没有定位真值，无法证明框或关节正确。
75是历史现场数据上的经验分界，单位为图像平均BT.601亮度0–255，不能解释为75 lux，也不是适用于所有摄像头的物理阈值。

## 三、先验规则把检测误差进一步放大

检查的是当前部署源码，不只是历史说明：

1. **漏检直接变成反证。** `object_prior.py` 的 `_drink()`、`_pickup()` 在正常推理但没检测到目标时返回False，随后 `_decide_max_prior()` 将动作改为other。检测器加载失败返回None时却放行。同一种“缺少可用证据”存在两种相反处理。
2. **无合格骨架仍可否决。** `_decide_max_prior()` 没有在 `info['p'] is None` 或 `valid` 全False时跳过先验。独立合成输入：RGB给drink 0.9、原图亮度100、零合格骨架；检测器不可用时输出drink，检测器正常但返回空框时输出other。这与模块注释中的“无骨架不做二次判断”和“缺失证据不拒绝”不一致。[复现结果](controls.json)
3. **静态几何只能提供弱证据。** 容器靠近手腕不能证明喝水；两个手腕接近不能证明握手；物体在脚边不能证明正在捡起；手肘/手腕高于躯干中线不能证明挥手。规则没有充分验证连续动作和接触关系。
4. **多人缺少稳定关联。** `skeleton_aux._fill_slots()` 按每帧关键点分数排序，没有跟踪；同一slot可在不同帧对应不同人。先验又遍历所有合格人，没有绑定到赢得动作分数的那个人。存在把A的动作与B的几何/物体证据组合的风险；此次只核实代码结构，未量化其实际误报占比。
5. **取最大分放大高分误判。** max_prior从最多6个骨架槽中选高分非other候选，再与RGB取高分；两类分数未做跨分支校准。它不能用“置信度更高”保证更正确，历史三部曲回放已经观察到大量骨架胜出误报。
6. **挥手分母与注释不一致。** `_wave()` 遇到所有腕/肘不可见时直接continue，因此这些帧不计入`seen`；注释却说计入。这会让少量可见抬手帧更容易超过30%比例。实际影响未在此次量化。

上述1/2是已复现的确定行为；3–6是可直接核实的规则/实现局限，并非本次给出了新的整套动作准确率。

## 四、排除了哪些基础故障

[controls.py](scripts/controls.py) 使用标准bus图和喝水16第34帧检查：

- ONNX能检出标准图中的公交车和4个人，模型并非完全失效。
- 诊断脚本在0.25阈值下与生产 `YoloOnnxDetector` 输出一致。
- 生产ONNX输出形状、COCO类号、RGB/归一化和坐标还原与代码假设一致。
- 与原始 `yolo26m-detect.pt` 对齐到同一端到端检测分支后，GPU框/分数结果接近；224个匹配融合参数张量的最大绝对差为3.06e-5以内。
- CPU/GPU对照都保留在 [controls.json](controls.json)。这不是完整ONNX精度认证，但本次未发现导出/后处理错误能解释所选样本漏检。
- 注意YOLO26m-pose与YOLO26m-detect是不同模型。历史“YOLO26漏检蹲伏人”的对比有一部分来自pose模型，不能直接当作detect模型的成绩；本次人体数字全部由detect权重实测。

复现时必须显式 `YOLO.predict(..., nms=False)`：当前Ultralytics预测接口的默认分支与既有端到端ONNX导出分支不同，直接用默认参数会形成不公平对照。该设置只用于诊断，不改变生产ONNX。

## 后续建议

优先把先验改为“支持 / 反对 / 不确定”三种证据状态：不可见、漏检风险高、无合格关键点时应进入不确定；明确负证据才参与否决。随后为人物建立稳定跟踪，再绑定手部、物体和动作。

检测侧优先保留原始帧中的人体/手部ROI，明确实际需要覆盖的物体类别，并补充本摄像头小物体和暗场的人体框/关键点标注，验证局部检测与领域微调。单纯增大显示输出、降低检测阈值或提高动作阈值不能代替这一步。

增强侧应单独评估原图、增强图及针对噪声的处理对检测/姿态的收益，允许展示增强图与检测输入采用不同选择。此次数据不足以直接决定全局切换到原图检测。

当前默认仍为alpha加权融合+原图亮度门75，物体先验仅在可选max_prior模式使用。`reco_min_conf=0.75`是动作输出阈值，与本次扫描的物体检测阈值0.25/0.1/0.05不同。

```bash
YOLO_CONFIG_DIR=/tmp/darkpipe-prior-diagnostic-yolo .venv/bin/python reports/prior-diagnosis-20261022/scripts/controls.py
```

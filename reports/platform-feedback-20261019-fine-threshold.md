## 2. 如何选择

**根据这次细扫，建议把下一轮平台试用值从先前建议的 0.70 更新为 0.73。**

- 0.73：本批误报 26 条，比 0.65 的 72 条减少 **63.9%**，比 0.70 的 39 条再少 **33.3%**。
  A176/177、C18/18 与 0.70 一样；没有比 0.70 新增回归漏检。但相对原 0.65，A 仍少一个喝水窗口。
- 0.74：只比 0.73 少 2 条误报，却开始拒掉 C 的挥手全片窗口（置信度 0.738101）。
- 0.75：比 0.74 再少 1 条误报，A 又损失一个挥手窗口。
- 0.78：若更偏重压误报，可作为更严格的对照档，剩 15 条，比 0.65 减少 79.2%；
  代价是 A174/177、C17/18，即比 0.73 再损失 A 两个窗口和 C 一个窗口。
- 0.80：与 0.79 一样剩 13 条误报，却多损失 A 两个窗口，本批数据不支持选它。

阈值细扫不是独立泛化验证：A/B/C 对现役拟合线属于训练内数据，P 也已用于 pn 加训。
0.73 仍有 26 条本批误报，不是彻底消除误报的门限。推荐是下一轮平台对照的起点，不能保证
新场景维持本表成绩。本次仅测试，**交付包默认 `reco_min_conf` 仍为 0.65**；使用 0.73 需要平台显式填写。

## 3. 现在是否还会中断

**已修复并验证的是“队列拥塞导致 end 消息被丢弃，随后服务异常退出”这一具体路径，
不能据此承诺任何条件下永不中断。** 当前仍会将真实编码、文件写入失败以及收尾时持续无进展
作为错误上报。本轮没有进行平台多小时或多天连续运行验收。

为补充上轮 96 项回归和真实 1440×874 quality/H.264 测试，本轮直接使用已交付 TAR 解包代码，
在同一 0.3.0 镜像内补测以下情况：队列上限分别为 4、8、64，每组 21 轮，反复人为暂停写线程
使队列填满；交替测试普通 post 收尾和两次确认后的动作切换；最后在录制中且队列拥塞时主动停止。
这组使用真实 ffmpeg H.264 编码，图像缩为 64×48、关闭去噪并人为暂停写线程，目的是验证
控制消息顺序和资源释放，不衡量完整尺寸 quality 的吞吐，也不运行行为模型。

| 补测指标 | 结果 |
|---|---:|
| 队列配置 | 4 / 8 / 64（64 为当前默认） |
| 拥塞轮次 | 63 |
| 行为切换 | 30 |
| 拥塞中的主动停止 | 3 |
| 正常保存片段 | 93 |
| 丢失收尾 / 强制释放 / 写盘错误 | 0 / 0 / 0 |
| 放弃 / 未完成 / 失败片段 | 0 / 0 / 0 |
| 全部视频完整解码 | 93/93 |
| 普通帧因拥塞丢弃 | 279 |
| push 最大耗时 | 0.708 ms |

新增 3 项连续片段测试与原 3 项针对性测试共 **6 项通过，26.18 秒**。

普通帧丢弃仍属于既有实时过载策略；补帧只能维持时长，不能恢复运动细节。上述结果支持
此次收尾修复在这些受控拥塞条件下有效，不把测试范围外的基础设施故障混为“已保证不会中断”。
